# ToolsGCP 版本命名规则

> 生效版本：**`v1.0.0-beta.1` 起**（这是本项目的第一个正式命名的版本）
> 唯一事实来源：`.ToolsGCP/modules/pymodels/constants.py` → `APP_VERSION`
> 配套文档：`docs/UPDATE_PLAN.md`（自动更新方案）

> 📌 **关于"版本从头开始"这件事**
> 之前的工作目录叫 `v1.1.4 - 12`，那个 `1.1.4` 是**随手起的**，不是真实发布的版本号
> （项目当时根本还没有任何 Release，本地也没有 git tag）。
> 现在统一从**最低的 `v1.0.0-beta.1` 重新起算**，本文档以下所有规则都以这个为起点。
> 目录名不参与版本控制，可以不管它。

---

## 一、一句话规则

```
版本号 = v主版本.次版本.修订号[-预发布标识]

  正式版：  v1.1.4          v1.2.0          v2.0.0
  测试版：  v1.2.0-beta.1   v1.2.0-beta.2   v1.2.0-rc.1

  · tag 名带 v，程序里的 APP_VERSION 不带 v
  · 三段都是数字，只增不减
  · 预发布标识写在 "-" 后面，用 - 分隔
  · 一旦发出去，永不修改、永不重用
```

**一句话：加 beta，但要按语义化版本（SemVer 2.0.0）的规范加，而不是随便在末尾糊一个 "beta"。**

---

## 二、为什么是 `vX.Y.Z`（这个"原理"你也问了）

这套规则不是随便定的，它有个正式名字：**语义化版本（Semantic Versioning 2.0.0）**，业界通用标准。

它解决的核心问题是：**让程序能自动判断"哪个更新"**。

如果版本号是 `v1.1.4 - 12` 这种自由格式，程序没法可靠地比较大小（`- 12` 是什么意思？数字还是日期？）。
而 `1.1.4` 这种"三段数字"是**可以机械比较**的：

```
把 1.1.10 和 1.1.4 都拆成整数元组：
  1.1.10 → (1, 1, 10)
  1.1.4  → (1, 1,  4)
  逐位比较 → 10 > 4 → 1.1.10 更新 ✅

如果直接比字符串（错误做法）：
  "1.1.10" < "1.1.4"   ← 因为逐字符比到第三位时 '1' < '4'
  → 第 10 个补丁版本永远更新不出去 ❌
```

**这就是为什么必须有规则。** 你的自动更新器要判断大小，版本号就必须是它能解析的格式。

### 三段的含义

| 段位 | 名字 | 含义 | 什么时候 +1 |
|---|---|---|---|
| 第 1 段 | **MAJOR 主版本** | 不兼容的重大变化 | 破坏性改动 |
| 第 2 段 | **MINOR 次版本** | 向下兼容的新功能 | 加功能 |
| 第 3 段 | **PATCH 修订号** | 向下兼容的问题修复 | 修 bug |

**递增规则（很重要）：**
- `MAJOR` +1 时，`MINOR` 和 `PATCH` **必须归零** → `1.4.7` → `2.0.0`
- `MINOR` +1 时，`PATCH` **必须归零** → `1.4.7` → `1.5.0`
- **所以不允许出现 `1.4.7` → `1.5.3` 这种跳法。**

## 三、三段号在 ToolsGCP 里具体怎么判断

通用定义太抽象，下面是我建议的、针对你**这个程序**的落地标准。

### MAJOR（主版本）—— 很少动，预计一年最多一次

满足**任意一条**才 +1：

- 配置文件格式发生**不兼容**变化（老版本的 `toolsgcp_config.json` 新版本读不了）
- `ToolsGCP-Resources.json` 资源库 schema 大版本变更（现在是 `schema_version: 2.1.0`），导致老版本读不了新资源库
- 插件 API 不兼容变更（已发布插件会失效）
- 界面被整体重做，用户需要重新学习怎么用
- 支持的运行环境变了（比如不再支持某个 Windows 版本）

**判断口诀：装回老版本会出问题的，才叫主版本。**

### MINOR（次版本）—— 有用户能感知的新东西

满足**任意一条**：

- 新增页面 / 板块（比如又加了一个「工具箱」）
- GCP-AI 新增能力（新的对话模式、新工具调用）
- 新增语言（加一门语言 = 一次 MINOR）
- 新增设置项且带新功能
- 新增插件体系能力

**判断口诀：用户升级后能说"哇，多了个东西"。**

### PATCH（修订号）—— 最常用，绝大多数发布都是它

满足**任意一条**：

- 修 bug（崩溃、显示错位、逻辑错）
- 文案 / 翻译修正
- 图标替换、图片资源更新
- **资源库数据更新**（`ToolsGCP-Resources.json` 增删条目、改下载地址）← 见 §6
- 内部重构、日志格式调整、性能优化，用户看不出区别
- 主题配色微调

**判断口诀：用户升级后说"好像稳了/正常了"。**

### 实际对照表（本项目从 v1.0.0-beta.1 起算）

| 版本 | 类型 | 举例 |
|---|---|---|
| **`v1.0.0-beta.1`** | 预发布 | ← **当前版本**（第一个对外发布的测试版） |
| `v1.0.0-beta.2` | 预发布 | beta 期间又修了几个问题 |
| `v1.0.0-rc.1` | 预发布 | 正式版之前的最后一道关 |
| `v1.0.0` | **首个正式版** | 宣告"1.0 稳定了"，项目对外的正式起点 |
| `v1.0.1` | PATCH | 修一个启动崩溃 |
| `v1.1.0` | MINOR | 新增 GCP-AI 侧边栏 |
| `v1.1.1` | PATCH | 修 AI 对话历史丢失 |
| `v1.2.0` | MINOR | 新增了一个页面 |

⚠️ 注意这里没有"1.0.0 必须先于 1.0.0-beta.1"的矛盾 ——
按 SemVer，`1.0.0-beta.1 < 1.0.0`，也就是说**预发布版本来就是"1.0.0 的候选"**，
先发候选、跑稳了再发正式版，这正是这套规则的设计意图。

## 四、要不要加 beta？—— **要，方案如下**

**明确回答：要加。** 理由：

1. 你现在"想随便发布几个试试"——**测试版需要一个名字**，否则测试包和正式包长得一模一样，用户分不清自己装的是哪个。
2. 你已经有 CI 自动发版了，加一个 prerelease 只是 tag 名字的区别，**成本几乎为零**。
3. 自更新上线后，如果测试版被当成正式版推给所有人，会出事故。**beta 机制就是防这个的。**

### 4.1 预发布标识的用词规范

按"从糙到精"的顺序，**只允许用这三个词**：

| 标识 | 含义 | 给谁用 | 例 |
|---|---|---|---|
| `alpha` | 内部开发版，功能可能只做了一半 | 只有你自己 | `v1.2.0-alpha.1` |
| `beta` | 功能做完了，但还没充分测试 | 愿意帮忙试的用户 | `v1.2.0-beta.1` |
| `rc` | Release Candidate，**除非发现严重 bug，否则这就是正式版** | 提前尝鲜的用户 | `v1.2.0-rc.1` |

**预发布序号从 1 开始，逐次递增：`beta.1` → `beta.2` → `beta.3`。**

### 4.2 排序规则（更新器必须实现，也是你判断"该不该升"的依据）

```
1.2.0-alpha.1  <  1.2.0-alpha.2
               <  1.2.0-beta.1
               <  1.2.0-beta.2
               <  1.2.0-beta.10     ← 注意 10 > 2，不是字符串比较
               <  1.2.0-rc.1
               <  1.2.0             ← 正式版永远大于自己的所有预发布版
```

**两条铁律：**
1. **正式版 > 同号的所有预发布版**：`1.2.0 > 1.2.0-rc.1`
2. **预发布版 < 同号正式版，但 > 上一号正式版**：`1.1.9 < 1.2.0-beta.1 < 1.2.0`
   （也就是说：装了 `1.1.9` 的人，收到 `1.2.0-beta.1` 时会认为"有新版本"——这是对的）

### 4.3 GitHub 侧必须做的一件事（⚠️ 现在的 CI 漏了）

`.github/workflows/release.yml` 目前的发布步骤**没有显式设置 `prerelease`**：

```yaml
      - name: 发布到 Release
        if: startsWith(github.ref, 'refs/tags/')
        uses: softprops/action-gh-release@v2
        with:
          files: |
            dist/ToolsGCP.exe
            dist/ToolsGCP-ResourceMaker.exe
            dist/SHA256SUMS.txt
          generate_release_notes: true
          # ← 这里缺了 prerelease
```

**风险：`v1.2.0-beta.1` 有可能被当成"完整发布"。**
一旦它是完整发布，`/releases/latest` 就会返回它 → **所有正式通道用户都会被推一个 beta 版**。

**改法（一行，用 tag 名自动判断，不依赖 action 的默认行为）：**

```yaml
          prerelease: ${{ contains(github.ref_name, '-') }}
```

同时建议顺手把 Release 标题写好看点（现在标题默认就是 tag 名）：

```yaml
          name: ToolsGCP ${{ github.ref_name }}
```

### 4.4 客户端侧：更新通道

「关于」页加一个下拉框，默认**稳定版**：

| 通道 | 接受哪些 Release | 适合谁 |
|---|---|---|
| **稳定版**（默认） | `prerelease == false` | 绝大多数用户 |
| **测试版** | 全部（含 prerelease） | 愿意帮忙试的人 |

⚠️ 通道过滤的价值：`draft`（草稿）对匿名 API **完全不可见**，所以草稿可以放心用来做"先自己试装"；
`prerelease` 则要靠上面那个 `prerelease: true` 才能被稳定通道排除。

## 五、tag 名 / `APP_VERSION` / 界面显示，三者的关系

**这是最容易搞混的地方，请按这张表来：**

| 位置 | 格式 | 例子 | 说明 |
|---|---|---|---|
| **git tag / Release 名** | 带 `v` | `v1.1.4`、`v1.2.0-beta.1` | 给人看的，`v` 是行业惯例 |
| **`constants.py` 的 `APP_VERSION`** | **不带 `v`** | `1.1.4` | 给机器比的，一个 `v` 都不要有 |
| **界面显示** | 带 `v` | `ToolsGCP v1.1.4` | 和 tag 保持一致，用户看到的和 Release 页面对得上 |
| **Linux/文件名里** | 带 `v` | `ToolsGCP-v1.1.4.zip` | 文件名按惯例带 `v` |

**⚠️ 关于更新载荷的文件名，有一个例外，而且是硬性要求：**

> **`ToolsGCP.exe` 这个名字里永远不写版本号。**

原因：自更新的"目标识别"就是按文件名精确匹配的（见 `UPDATE_PLAN.md` §3）。
一旦改成 `ToolsGCP-1.1.5.exe`，更新器就必须先解析 tag 才知道该下哪个文件——版本号和文件名两个变量互相纠缠，出错的概率立刻翻倍。
保持恒定名字 = **更新器永远不需要解析 tag 就能找到文件**。

如果你觉得"下载页看到带版本号的文件名更清楚"，可以发 Release 时**额外**放一份带版本号的副本，但**不带版本号的那份是唯一权威**：

```
🔒 ToolsGCP.exe              ← 权威，更新器只认它（必需）
   ToolsGCP-1.1.5.exe        ← 可选，方便人类手动下载（会增加一倍体积）
   SHA256SUMS.txt            ← 校验清单（建议必发）
   ToolsGCP-ResourceMaker.exe ← 另一个程序，更新器永不选它
```

### `v` 前缀的处理规则（更新器容错用）

```
解析时应先剥掉开头的 v / V：  "v1.1.4" → "1.1.4"     "V1.1.4" → "1.1.4"
但**生成** tag 时只允许小写 v： tag 必须是 "v1.1.4"，不是 "V1.1.4"
```
"宽进严出"——读的时候宽容，写的时候严格。

## 六、特殊情况：不发代码、只更新资源库怎么办？

你有一个别的程序没有的特殊情况：**`ToolsGCP-Resources.json`（资源库）会独立于代码更新。**
比如你只是给某个工具换了个下载地址，或者加了 20 个新条目——一行 Python 代码都没改。

**这时候也必须发一个新版本号（PATCH）。** 建议规则：

| 情况 | 版本怎么动 | 例子 |
|---|---|---|
| 只更新资源库数据 | **PATCH +1** | `v1.1.4` → `v1.1.5` |
| 若干条资源库更新积累到一定量 | 也可以攒着，等有代码改动时合并发布 | — |
| 只想给测试用户试资源库 | 发 prerelease | `v1.1.5-beta.1` |

**为什么必须发版本号而不能"悄悄推一个文件"：**

因为自动更新是**由版本号驱动的**。没有新版本号，客户端的更新器就不会知道"资源库变了"，用户永远不会主动来下载。
换句话说：**版本号是"有新东西"的唯一信号。**

⚠️ 注意这里的代价：资源库是打包进 exe 的（`--add-data ".ToolsGCP;.ToolsGCP"`），
所以"只改资源库"目前意味着**用户要重新下载几十 MB 的 exe**。
如果以后觉得太浪费，可以走 `UPDATE_PLAN.md` §4.8 的**方案乙**（额外发一个小的资源包）。在当前阶段，用 PATCH 版本号是最简单可靠的。

## 七、构建号（build number）的正确写法

你的工作目录曾经叫 **`v1.1.4 - 12`**——那个名字里的 `1.1.4` 是随手起的（本地没有 git tag，
也没有对应的 Release），后面的 `12` 才是"第 12 次迭代"的意思。

**既然要正式发版了，这两样都不能再这么写。** 正确的写法是用 SemVer 的 **build 元数据**：

```
v1.0.0-beta.1+build.12       ← 加号后面是构建元数据
```

**规则：**
- 构建元数据（`+` 后面）**不参与版本比较**。`1.0.0+build.12` 和 `1.0.0+build.3` 被视为**同一个版本**。
- 所以它**只能用于本地开发记录，永远不要用在 Release tag 上**。

**为什么？** 因为更新器比大小的时候会**忽略** `+build.12`。
如果你发了 `v1.0.0+build.12`，已有的 `v1.0.0` 用户会看到"版本相同"→ **收不到更新**。
这就白发了。

**推荐做法：**

| 场景 | 怎么写 |
|---|---|
| 本地开发第 12 次迭代 | 文件夹叫什么都行，或者记成注释 `# build 12` |
| 想让测试用户拿到第 12 次迭代 | **改预发布序号** → `v1.0.0-beta.12` |
| 想给正式用户 | `v1.0.0`（功能稳定之后） |

**一句话：要让人收到更新，就动小数点，别动加号。**

## 八、禁止清单（❌ 这些写法一律不许用）

| ❌ 错误写法 | 问题 | ✅ 正确写法 |
|---|---|---|
| `V1.1.5` | 大写 V，惯例是小写 | `v1.1.5` |
| `1.1.5`（tag 不带 v） | 与项目惯例不符，CI 的 `v*` 触发器也匹配不到 | `v1.1.5` |
| `v1.1.5 final` / `v1.1.5-正式版` | **含空格/中文，更新器无法解析** | `v1.1.5` |
| `v1.1.5.12` | 四段数字，不是标准三段的 SemVer | `v1.1.5` 或 `v1.1.5+build.12` |
| `v1.1.5+build.12`（用在 Release） | build 元数据不参与比较 → 用户收不到更新 | `v1.1.5` |
| `v1.1` | 两段，无法可靠比较 | `v1.1.0` |
| `v01.1.5` | 前导零，非法 | `v1.1.5` |
| `latest` / `v最新` | 不是版本号 | `v1.1.5` |
| `v2026.10.06`（日期） | 不是 SemVer；日期无法表达"兼容性"语义 | `v1.1.5` |
| `v1.5.3`（从 `v1.4.7` 跳） | 违反"MINOR +1 时 PATCH 归零" | `v1.5.0` |
| `v1.1.5-beta`（无序号） | 第二次 beta 就没法命名了 | `v1.1.5-beta.1` |
| `v1.1.5-Beta.1` / `v1.1.5-BETA.1` | 预发布标识**区分大小写**，会变成两个不同版本 | `v1.1.5-beta.1` |
| 删除已发布的 tag 再重发同名 tag | 用户可能已缓存该版本，会出现"提示更新→又消失" | 发 `v1.1.6` 修正 |
| 修改已发布 Release 里的 exe | 哈希变了、用户已装的没变，状态不一致 | 发新 PATCH 版本 |

## 九、发布操作手册（照着做即可）

### 正式版发布流程

```bash
# 1. 改版本号（唯一事实来源！）
#    .ToolsGCP/modules/pymodels/constants.py
#    APP_VERSION = "1.0.0"          ← 不带 v！
#    （发 beta 就写 "1.0.0-beta.2"，依此类推）

# 2. 本地跑一遍确认没坏
python ToolsGCP.pyw

# 3. 提交并推送到 GitHub
git add -A
git commit -m "release: v1.0.0"
git push

# 4. 打 tag 并推送  ← 这一步会自动触发 CI 打包并发布
git tag v1.0.0
git push origin v1.0.0

# 5. 去 Actions 页面看流水线是否绿
# 6. 去 Releases 页面确认：tag 名、prerelease 状态、ToolsGCP.exe 是否在里面
```

### 测试版发布流程（本项目当前就在这个阶段）

```bash
# 和正式版完全相同，只是 tag 带预发布标识
git tag v1.0.0-beta.1
git push origin v1.0.0-beta.1
# ⚠️ 发完必须确认 Release 上有 "Pre-release" 标签
#    如果没有 → 说明 CI 的 prerelease 配置没生效 → 正式用户会被推 beta！
```

### 发布前检查清单

- [ ] `constants.py` 的 `APP_VERSION` 已改，且与 tag 一致（去掉 tag 的 `v` 后应当完全相同）
- [ ] 没在 `pymodels/__init__.py` 里另写一个版本号（它已改成从 constants 转发）
- [ ] tag 名符合 §8 的规定（小写 v、三段数字、无空格中文）
- [ ] 若是测试版：Release 上有 "Pre-release" 标签
- [ ] Release 里确实有 `ToolsGCP.exe` 和 `SHA256SUMS.txt`
- [ ] Release 说明写清楚了改了什么（**更新弹窗会把这段文字原样显示给用户**，见下）

> 💡 **Release 说明就是更新弹窗的正文。**
> 更新器读取的是 Release 的 `body` 字段，会原样展示给用户。
> 所以建议格式（配合 `generate_release_notes: true` 自动生成的部分）：
>
> ```markdown
> ## 更新内容
> - 修复了 xxx 崩溃的问题
> - 资源库新增 20 个条目
>
> ## 注意事项
> - 本次更新需要重启程序
> ```
>
> ⚠️ 一个细节：`generate_release_notes: true` 生成的说明依赖**上一个 tag 做对比**。
> 你现在本地还没打过 tag，所以**第一个 Release 的自动说明会是空的**，需要手写。
> 建议同时维护一份 `CHANGELOG.md`。

## 十、更新器解析版本时的容错规则（写给实现者）

| 输入 | 行为 |
|---|---|
| `v1.1.4` | ✅ 正常解析 |
| `1.1.4` | ✅ 正常解析（tag 少了 v 也能忍） |
| `V1.1.4` | ✅ 正常解析（宽容读取） |
| `v1.1.4+build.12` | ✅ 解析成功，但 **build 部分被忽略**（视为 1.1.4） |
| `v1.2.0-beta.1` | ✅ 解析为预发布版，按 §4.2 排序 |
| `v1.1.4 正式版` | ❌ **解析失败 → 拒绝更新 + 记日志**，绝不猜 |
| `v1.1.4.12` | ❌ 解析失败 → 拒绝更新 |
| 空 / `null` | ❌ 忽略该 Release，继续看下一个 |

**核心原则：宁可"不更新"，也绝不"猜一个大小"。**
一次错误方向的自更新（比如把用户从 1.1.10 降到 1.1.4）比不更新严重得多。

## 十一、常见问题

**Q：我要不要每个小改动都发一个版本？**
A：不用。攒着一起发。但记住 §6：**资源库更新也必须通过发版本号才能让用户拿到**。

**Q：能不能发一个 `v1.0.0` 然后偷偷把里面的 exe 换成新的？**
A：**不能。** 已经装了的用户版本号相同 → 更新器认为"已是最新" → 永远收不到；
而且你的 `SHA256SUMS.txt` 会和缓存对不上，排查起来极其费劲。**永远发新版本号。**

**Q：beta 要不要一直加序号？**
A：要。`beta.1` → `beta.2` → …… 直接跳到 `rc.1` 也可以。但**不许回头**（发过 `beta.3` 就不能再发 `beta.2`）。

**Q：`v1.0.0-beta.1` 发现严重 bug，我已经推了 tag 了怎么办？**
A：**不要删 tag 重发。** 直接发 `v1.0.0-beta.2` 修复，并在 Release 说明里写"撤回 beta.1"。
删 tag 会导致已缓存的客户端出现"提示更新 → 又消失"的诡异现象。

**Q：以前有两个版本号（`constants.py` 是 `1.1.4`，`__init__.py` 是 `1.0.0`），现在呢？**
A：✅ **已经统一了。** `constants.py` 的 `APP_VERSION`（现为 `1.0.0-beta.1`）是唯一来源，
`pymodels/__init__.py` 的 `__version__` 已改成 `from .constants import APP_VERSION as __version__`。
以后改版本**只改 `constants.py` 一处**。

**Q：目录名还是 `v1.1.4 - 12`，要不要改？**
A：不用。目录名不参与任何版本判断，也不影响更新器。版本号只认 `constants.py` 的 `APP_VERSION` 和 git tag。
（真要改也无所谓，但改了记得同步本地路径，别让脚本找不到。）

**Q：版本号里的 `v` 到底该不该有？每次都要想一下。**
A：记这一句就够：**"给人看的地方都有 v（tag、界面、文件名），给机器比的地方都没有 v（APP_VERSION）"。**
